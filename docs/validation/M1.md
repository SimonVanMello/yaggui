# Manual validation of milestone M1

Guide for validating M1 (read-only features: graph, refs sidebar, commit detail and diff, palette, performance) on **macOS** and **Windows** before starting M2. Allow about 45 minutes per OS. Prerequisites, launching and database location: same as [M0.md](M0.md) §1–2.

```bash
git pull && pnpm install
pnpm tauri dev                       # dev mode
pnpm tauri build --no-bundle         # release binary, for the performance items
```

Performance is judged **on the release binary**, not under `pnpm tauri dev`.

## 1. Test repositories

| Repository | Setup | Used for |
|---|---|---|
| A normal-sized personal repository | — | everyday use, working tree diff |
| `git/git` | `git clone https://github.com/git/git.git` (~75k commits) | P-02, graph, search |
| `torvalds/linux` | `git clone https://github.com/torvalds/linux.git` (~1.3M commits, several GB; `--filter=blob:none` is enough) | P-03, P-04, "scaled" scrolling |

To test the first display **without** a commit-graph, delete it before opening the repository: `rm -rf .git/objects/info/commit-graph .git/objects/info/commit-graphs` (on Windows: delete these two entries in File Explorer).

## 2. Checklist

Tick each item; "Expected" describes the correct behavior. OS-specific items are marked **(mac)** or **(win)**. `⌘` = `Ctrl` on Windows.

### Commit graph

- [ ] **Open the personal repository** — Expected: graph shown with colored lanes, a "Work in progress" node at the top if the working tree is dirty, branch / tag / stash pills on the right commits, message, author, date and SHA columns.
- [ ] **HiDPI rendering** (Retina display / Windows at 150 %) — Expected: crisp lines and nodes, not blurry nor offset from the row text.
- [ ] **Columns**: resize, then close and reopen the tab — Expected: widths are kept.
- [ ] **Keyboard**: ↑/↓, PgUp/PgDn, Home/End in the graph — Expected: the selection follows and stays visible; the right panel shows the commit detail.
- [ ] **Context menu** (right-click, then Shift+F10 from the keyboard) — Expected: M2 actions are greyed out, "Copy SHA" / "Copy message" work.
- [ ] **Search ⌘F** on `git/git` (e.g. `revert`) — Expected: results arrive in batches without freezing the UI, navigation between results, the graph scrolls to the commit.
- [ ] **External commit/checkout** (in a terminal, on the open repository) — Expected: the graph and refs update on their own in under a second, without losing the scroll position.

### Refs sidebar

- [ ] **Sections** Local / Remote / Tags / Stashes / Submodules / Worktrees — Expected: tree grouped by prefix (`feat/…`), counters, ahead/behind ↑↓ on tracking branches, "upstream deleted" on a branch whose upstream is gone.
- [ ] **Click on a branch or a tag** — Expected: the graph scrolls to the commit and selects it, even when it is very far down (try an old `git/git` tag, e.g. `v1.0.0`).
- [ ] **Filter ⌘⇧R** — Expected: focus in the field, immediate filtering, ↓ moves into the tree, Esc clears then leaves.
- [ ] **Keyboard in the tree**: arrows, ←/→ to collapse/expand, Shift+F10 for the menu — Expected: works without a mouse.
- [ ] **Collapse sections**, then switch tabs back and forth — Expected: state is kept per tab.
- [ ] **Double-click on a branch** — Expected: "Soon" tooltip (checkout comes in M2), nothing happens in the repository.

### Commit detail and diff

- [ ] **Select a commit** — Expected: author, date, copyable SHA, clickable parents, refs, file list (list or tree) with status and +/−.
- [ ] **Click on a file** — Expected: the diff replaces the graph in the center; Esc goes back to the graph at the same position.
- [ ] **Unified / Side by side** (⌘D) — Expected: immediate switch, choice kept after a restart; in side by side, vertical and horizontal scrolling are synchronized.
- [ ] **Navigation** `n`/`p` (next/previous change), `j`/`k` (next/previous file) — Expected: works when focus is not in a text field.
- [ ] **Syntax highlighting** on a `.ts`, `.rs`, `.py` — Expected: appears right after display, without flicker.
- [ ] **Edge cases** (in the personal repository, or create them): rename, binary / image, file > 1 MB ("Show anyway"), deletion, chmod — Expected: dedicated banner or state, never a crash or a freeze.
- [ ] **Working tree**: modify a tracked file, select the WIP row — Expected: files under "Unstaged", correct diff, updated on save.
- [ ] **(win)** With `core.autocrlf=true` (Git for Windows default), modify one line of a file — Expected: only that line shows up, not the whole file as a CRLF difference.
- [ ] **(win)** `core.fileMode=false` — Expected: no spurious mode change.

### Palette ⌘K

- [ ] **⌘K** (mac) / **Ctrl+K** (win) — Expected: the palette opens, recent items first.
- [ ] **Mixed search**: type part of a branch name, of an action ("theme"), of a commit message — Expected: relevant sorted results, ↵ runs the item; a branch or a commit scrolls the graph.
- [ ] **Prefixes** `>` actions, `@` refs, `#` commits, `/` files — Expected: filter by category.
- [ ] **M2 actions** (Pull, Push, Commit…) — Expected: visible but greyed out.
- [ ] **Focus after running an action** (e.g. "Filter branches and tags", "Open the external terminal in the repository") — Expected: focus goes to the right place, not lost in the page.

### Performance (release binary)

- [ ] **P-02 · `git/git`, second open** (close the tab, reopen) — Expected: graph shown in under 300 ms.
- [ ] **First display without commit-graph** (see §1) — Expected: `git/git` < 1 s; then the Command log (status bar) shows a `git commit-graph write` in the background, with no toast; when it finishes, the graph reloads **without a scroll jump**.
- [ ] **An operation during that write** (e.g. open the diff, switch tabs) — Expected: no noticeable slowdown.
- [ ] **P-03 · `linux`, opened once the commit-graph is written** — Expected: graph in ~1 s. The very first display without commit-graph takes several seconds (known limitation, see §3): the UI must stay responsive meanwhile.
- [ ] **P-04 · scrolling `linux`** (mouse wheel, trackpad, dragging the thumb) — Expected: smooth, no blank rows, no canvas offset from the text. Note how it feels on a modest machine if one is available.
- [ ] **"Scaled" scrolling** on `linux` (history > 350k rows): End, then drag the thumb all the way up, **(mac)** trackpad with inertia — Expected: reaches the first and the last commit; no jump during inertia.
- [ ] **Repository with large `node_modules` / `target`** — Expected: instant open; an `npm install` in that folder does not slow yaggui down.
- [ ] **P-08 · palette** on `linux` — Expected: typing without noticeable latency.

### Themes

- [ ] **Graphite and Paper** on every screen above — Expected: correct contrast, pills and lane colors readable in both.

## 3. Known limitations (accepted for M1)

- **First display of a very large repository never opened before, without commit-graph**: the full history order is computed before the first page (~0.7 s on `git/git`, ~8 s on a 1.3M-commit repository, measured on Linux). The commit-graph is then written in the background and later opens are fast. Can be improved later by serving the first page before the computation ends.
- **P-04 on a slow machine**: 60 fps measured at normal CPU; ~20 fps with ×4 CPU throttling in a Chromium **without GPU**. Feedback from WKWebView / WebView2 with a GPU decides whether to go further (drawing avatars, date and SHA in the canvas).
- **Checkout, menu actions, staging, commit**: M2. Anything that writes to the repository is greyed out.
- **Diff**: no line wrapping (F-082) nor image comparison (F-085), planned for M2.
- **Palette**: "files" means the changed files of the selected commit or of the working tree, not every file in the repository; recent repositories that are not open are not listed; no entry in the macOS menu.
- **(win)** Still no Snap Layouts menu when hovering the Maximize button (see M0).

## 4. Reference measurements (Linux container, 4 vCPU, no GPU)

| Target | Requirement | Measured |
|---|---|---|
| P-02 `git/git`, with commit-graph | < 300 ms | 38 ms |
| P-02 `git/git`, without commit-graph | < 300 ms | 697 ms ❌ (once only, then commit-graph written in 8.3 s in the background) |
| P-03 1.3M commits, with commit-graph | < 1.5 s | 786 ms |
| P-03 1.3M commits, without commit-graph | < 1.5 s | 8.3 s ❌ (once only, written in 43 s in the background) |
| P-04 scrolling, CPU ×1 | 60 fps | 60 fps |
| P-04 scrolling, CPU ×4 | — | ~20 fps, p95 83 ms |
| P-06 4,800-line diff, selection → render | < 100 ms | median 46–61 ms (mock front end); backend 1.7 ms |
| P-08 palette, 10k items, per keystroke | < 30 ms | median 12.6 ms, p95 20.6 ms |
| Watcher, repository with `node_modules` + `target` | — | 72 watches (previously 4,463), open in 10 ms |
| `listRefs`, 23k refs | — | 0.7 s on first call, ~45 ms afterwards |

Details are in the M1 task PRs.

## 5. Expected report

For each failing item: OS, step, what was observed (screenshot if visual), and for performance the repository and the perceived smoothness or duration. Command log entries (status bar → Log) help for anything Git-related.
