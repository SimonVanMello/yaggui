Un bisect trouve le commit qui a introduit un bug en testant le moins de commits possible : vous indiquez quel commit est mauvais (le bug est là) et lequel est bon (il n’y est pas), yaggui extrait un commit à mi-chemin, vous le testez et le marquez, et ainsi de suite jusqu’à ce qu’il ne reste qu’un commit. yaggui lance [git bisect](https://git-scm.com/docs/git-bisect) à chaque étape.

## Démarrer un bisect

Faites un clic droit sur un commit du graphe et ouvrez **Démarrer un bisect** :

- **Marquer comme mauvais** : le bug est présent dans ce commit, en général HEAD ou le bout d’une branche.
- **Marquer comme bon** : le bug est absent, en général un commit plus ancien ou un tag de version.

Le premier marquage démarre le bisect (`git bisect start`, puis `git bisect bad <sha>` ou `git bisect good <sha>`). Une bannière apparaît au-dessus du graphe et demande l’autre marquage : « Marque un commit bon, où le bug est absent : HEAD avec les boutons, ou un commit plus ancien depuis son menu dans le graphe. » (ou le mauvais). Marquez-le de la même façon, depuis le menu d’un autre commit, désormais nommé **Bisect**, ou pour HEAD avec les boutons de la bannière.

Dès qu’un commit bon et un mauvais sont connus, Git extrait le commit à tester, en HEAD détachée.

Un bisect demande une copie de travail propre : chaque étape extrait un autre commit, et vos modifications seraient testées avec lui. Si des fichiers suivis ont des modifications locales, le marquage est refusé avec « Tu as des modifications locales : un bisect teste chaque commit tel qu'il a été commité. Mets-les de côté (stash) ou commite-les d'abord. » et une boîte de dialogue, **Mettre tes modifications de côté pour le bisect ?**, propose **Stash et continuer** : les modifications sont mises de côté (`git stash push`, message `yaggui : avant le bisect`) et le marquage est relancé. Les fichiers non suivis restent en place. Des fichiers en conflit refusent aussi le marquage.

Tant qu’une autre opération (merge, rebase, cherry-pick, revert) est en cours, **Démarrer un bisect** est désactivé.

## Tester et marquer chaque commit

La bannière affiche :

- **Test de** suivi du SHA court et du résumé du commit extrait. Cliquez dessus pour sélectionner le commit dans le graphe.
- **environ \{count\} étapes restantes · \{count\} commits à tester** : l’estimation que donne Git (« roughly N steps »), et les commits qui peuvent encore être le premier mauvais et ne sont pas encore testés.
- **Bon**, **Mauvais** et **Passer**, qui marquent le commit testé (HEAD) : `git bisect good`, `git bisect bad` ou `git bisect skip`. Utilisez **Passer** pour un commit impossible à tester, par exemple un commit qui ne compile pas.
- **Arrêter le bisect**, décrit dans [Terminer le bisect](#terminer-le-bisect).

Testez le commit (compilez-le, lancez-le, lancez le test qui échoue), puis cliquez sur le bouton qui correspond. Git extrait le commit suivant, la bannière se met à jour et la barre d’état indique **Bisect : étape faite**.

Vous pouvez aussi marquer n’importe quel commit depuis le graphe : clic droit, **Bisect**, puis **Marquer comme bon**, **Marquer comme mauvais** ou **Passer ce commit**. C’est utile quand vous connaissez déjà la réponse pour un commit autre que HEAD.

### Depuis la palette

La palette (<kbd>⌘K</kbd>, <kbd>Ctrl+K</kbd> sous Windows et Linux) propose **Bisect : marquer comme bon**, **Bisect : marquer comme mauvais**, **Bisect : passer le commit testé** et **Bisect : terminer et revenir au départ**. Pendant un bisect, les marquages s’appliquent au commit testé, comme les boutons du bandeau, quel que soit le commit sélectionné dans le graphe. Sans bisect, **Bisect : marquer comme bon** et **Bisect : marquer comme mauvais** marquent le commit sélectionné dans le graphe et en démarrent un, comme son menu. Une entrée qui ne peut pas s’exécuter est listée en grisé avec la raison : **Sélectionne d'abord un commit**, **Aucun bisect en cours**, **Aucun commit à marquer pour l'instant** (le résultat est connu, ou le commit suivant n’a pas pu être extrait) ou **Termine l'opération en cours**.

### Marqueurs dans le graphe

Pendant un bisect, le graphe affiche une pastille avant les étiquettes de refs des commits que le bisect connaît : **bon**, **mauvais**, **passé**, **en test** pour le commit extrait, et **premier mauvais** à la fin.

### Quand le commit suivant ne peut pas être extrait

Si un fichier non suivi gêne le commit suivant, le marquage est enregistré mais l’extraction échoue : « Le marquage est enregistré, mais le prochain commit à tester n'a pas pu être extrait : des fichiers gênent. Déplace-les ou supprime-les, puis extrais le commit suivant. » La bannière indique alors « Le prochain commit à tester n'a pas pu être extrait. » avec **Extraire le commit suivant** (`git bisect next`). Le même bouton apparaît si vous avez déplacé HEAD à la main sur un commit déjà marqué.

### Marquages dans le mauvais ordre

Si un commit bon vient après le mauvais dans l’historique, Git ne peut pas faire de bisect entre eux : « Un commit bon n'est pas un ancêtre du mauvais : Git ne peut pas faire de bisect entre eux. Vérifie les marquages, ou termine le bisect et recommence. » Les marquages ne peuvent pas être retirés un par un : arrêtez le bisect et recommencez.

## Bisect en mode premier parent

Si le graphe est en [mode premier parent](../commit-graph/#historique-premier-parent) quand vous donnez le premier marquage, yaggui démarre le bisect avec `git bisect start --first-parent` : seuls les commits de l’historique premier parent, ceux que le graphe affiche, sont extraits et testés. Un merge est testé en bloc : si le bug est venu avec une branche mergée, le premier commit mauvais est le merge. Le bandeau affiche une étiquette **Premier parent** (« Démarré en mode premier parent : seuls les commits de l'historique premier parent sont testés »), et ses étapes restantes et commits à tester ne comptent que ces commits. Le mode est celui du démarrage : activer ou désactiver le mode premier parent pendant un bisect ne change ni les commits testés ni les comptes.

`--first-parent` demande Git 2.29 ou plus récent. Avec un Git plus ancien, le bisect démarre sur tous les ancêtres et une notification indique **Bisect démarré sur tous les ancêtres** : « Cette version de Git ne sait pas faire de bisect le long des premiers parents (Git 2.29 ou plus récent) : les commits des branches mergées sont testés aussi. »

Quand il ne reste qu’un commit, la bannière indique **Premier commit mauvais trouvé** avec son SHA court, son résumé, son auteur et sa date. Une notification indique **Premier commit mauvais : \{sha\}** et le commit est sélectionné dans le graphe, avec ses détails dans le panneau de droite. **Voir le commit** le sélectionne à nouveau.

S’il ne reste que des commits passés entre les commits bons et le mauvais, Git ne peut pas dire lequel est le premier mauvais. La bannière indique **Bisect non concluant** et « Il ne reste que des commits passés : le premier commit mauvais est l'un de ces \{count\} », suivi de leurs SHA courts (cliquez sur l’un d’eux pour le sélectionner).

Si le commit mauvais est un ancêtre d’un commit bon, rien ne peut être testé. yaggui refuse de telles marques, mais `git bisect` dans un terminal les enregistre avant de refuser : un bisect démarré là peut être relu dans cet état. La bannière indique **Les marques du bisect se contredisent** et « Le commit mauvais est un ancêtre d'un commit bon : rien ne peut être testé. Marque un commit plus récent comme mauvais depuis son menu dans le graphe, ou termine le bisect. »

## Terminer le bisect

**Arrêter le bisect** (ou **Terminer le bisect** une fois le résultat connu) demande **Arrêter le bisect ?** « HEAD revient où il était avant le début du bisect. » et lance `git bisect reset` : la branche sur laquelle vous étiez est de nouveau extraite. Les marquages sont supprimés.

## Un bisect démarré ailleurs

yaggui lit le bisect dans le dossier `.git` : les marquages (`refs/bisect/`), le point de départ (`BISECT_START`) et les termes (`BISECT_TERMS`). Un bisect démarré dans un terminal, ou laissé ouvert à la fermeture de yaggui, affiche sa bannière et ses marqueurs à l’ouverture du dépôt, et vous pouvez le poursuivre. Un bisect démarré avec des termes personnalisés (`--term-old` / `--term-new`) est marqué avec eux ; yaggui les appelle toujours bon et mauvais. `git bisect run` n’est pas disponible depuis yaggui.

## Bisect et annulation

Les étapes du bisect ne figurent pas dans l’historique d’annulation : elles ne font que déplacer HEAD, et le retour en arrière passe par la réinitialisation du bisect. Tant qu’un bisect est en cours, l’annulation et le rétablissement sont refusés, comme pendant toute autre opération ; voir [Annuler et rétablir](../undo-and-redo/).
